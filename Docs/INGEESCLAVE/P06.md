# P06 — Comprendre la réservation d'une porte

- Lot : `P06`
- Statut : `waiting_human — tous les tests verts, vérification visuelle H2 non rapportée`
- Dernière mise à jour : `2026-08-15`
- Rapport technique associé : `.agents/ingeesclave/REPORTS/P06.md`

## En une phrase

P06 donne un ticket temporaire à une seule capsule pour traverser le seuil, tandis que les autres attendent leur tour.

## Pourquoi ce changement existe

Dans un couloir étroit, deux agents venant de côtés opposés peuvent se bloquer. Une file FIFO — « premier arrivé, premier servi » — rend l'ordre explicite et libère automatiquement un ticket abandonné.

## Vocabulaire utile

| Mot | Explication simple |
|---|---|
| FIFO | « Premier arrivé, premier servi » : le premier ticket demandé est le premier accordé. |
| Propriétaire | Objet précis qui possède temporairement le droit de traverser. |
| Expiration | Fin automatique d'un ticket qui n'est plus rafraîchi. |
| Point d'attente | Position de chaque côté où la capsule s'arrête avant le seuil. |
| Point de dégagement | Destination propre à une capsule, après la porte, où elle ne bloque plus le point d'attente partagé. |
| Passage | Contrat commun : peut-on l'utiliser, l'ouvrir et le réserver ? |

## Carte des responsabilités

```text
NpcDoorTraversal (AI)
        │ commandes IDoorPassage
        ▼
SlidingDoor ── DoorReservationQueue (Gameplay)
        │
        ├── conserve E + raycast joueur
        └── déplace le battant avec Rigidbody

NpcDoorTraversal ── commandes de déplacement ──> NpcMotor
```

| Fichier | Responsabilité |
|---|---|
| `IDoorPassage.cs` | Définit ce qu'un consommateur peut demander sans connaître `SlidingDoor`. |
| `DoorReservationQueue.cs` | Conserve l'ordre FIFO, le propriétaire et les expirations. |
| `SlidingDoor.cs` | Interaction joueur, animation physique et adaptation au contrat. |
| `NpcDoorTraversal.cs` | Enchaîne réservation, attente, ouverture, traversée et libération. |
| `NpcDoorTraversalStressProbe.cs` | Répète le scénario du sandbox jusqu'à vingt passages. |

## Déroulé d'une capsule

1. La capsule choisit le point d'attente le plus proche comme côté de départ.
2. Elle appelle `TryReserve`. Si un autre propriétaire passe, elle reste dans la file.
3. Quand elle devient propriétaire, `NpcMotor` la conduit au point d'attente.
4. Elle appelle `RequestOpen` et attend que `IsPassable` soit vrai.
5. Elle dépasse le point partagé et rejoint son point de dégagement propre de l'autre côté.
6. Elle appelle seulement alors `Release`; le propriétaire suivant est immédiatement promu.

Le même `Release` est utilisé après une mort, un disable, un reset et un timeout. Si un objet disparaît sans appeler proprement cette méthode, le ticket expire après cinq secondes dans le sandbox.

### Leçon tirée du premier test rouge

La première version terminait exactement sur le point d'attente opposé. La capsule suivante devait atteindre ce même emplacement avant de traverser : l'évitement l'arrêtait, puis `NpcMotor` épuisait ses recalculs. Augmenter le timeout aurait seulement attendu plus longtemps devant la même obstruction.

La correction conserve donc le point d'attente comme emplacement partagé avant la porte, mais donne à chaque capsule deux dégagements distincts. La réservation couvre tout le trajet jusqu'au dégagement. Le test ne désactive pas l'évitement et ne téléporte aucun agent.

## Pourquoi le joueur n'est pas couplé aux PNJ

`SlidingDoor` continue à lire la touche E et à vérifier ce que regarde la caméra. L'AI ne référence jamais cette classe concrète : elle reçoit un composant qui respecte `IDoorPassage`. La porte ne connaît ni `Guard`, ni Behavior node, ni faction.

## Essayer sans risque — porte H2

> État actuel : la correction compile, mais son mouvement doit être rejoué dans Unity. Relancer d'abord les deux tests opposés ; ne passer au Bake que lorsqu'ils sont verts.

### 1. Exécuter les tests

1. Dans la barre de menus Unity, ouvrir `Window > General > Test Runner`.
2. Choisir l'onglet `PlayMode`.
3. Déplier `GiscardPunk77.AI.PlayMode.Tests`, puis `NpcDoorTraversalPlayModeTests`.
4. Sélectionner `TwoCapsulesFromOppositeSidesCompleteInOrder` et cliquer `Run Selected`.
5. Faire de même avec `FourCapsulesFromOppositeSidesAllComplete`.
6. Si les deux sont verts, sélectionner l'assembly complet `GiscardPunk77.AI.PlayMode.Tests` et cliquer `Run Selected`. Unity entre et sort automatiquement du Play Mode pendant ces tests.

Le message `This XML file does not appear to have any style information associated with it` n'est pas un échec Unity. Il signifie seulement qu'un navigateur affiche le rapport XML brut sans mise en page. Les informations importantes sont les attributs `passed`, `failed` et les blocs des tests rouges.

Les nouveaux contrôles portent sur deux propriétaires, quatre propriétaires, expiration, deux capsules, quatre capsules, mort, disable, reset et timeout.

Dans les rapports reçus avant correction, les huit tests de cycle de vie et de moteur passent. Les deux scénarios opposés échouent parce que le premier point final est aussi le point d'approche suivant. Après correction, un éventuel timeout affichera pour chaque capsule son état, son échec, sa position et sa destination : transmettre ce nouveau texte plutôt que l'ancienne ligne `Expected True`.

### 2. Générer le stress test

Effectuer cette section seulement lorsque les dix tests Play Mode sont verts.

1. Dans la barre de menus Unity, choisir `Tools > GiscardPunk77 > P06 > Create or Update Door Stress Sandbox`. L'outil crée ou met à jour uniquement la racine générée.
2. Dans la fenêtre `Project`, ouvrir `Assets > _Project > Scenes > Tests`, puis double-cliquer `NpcSandbox`.
3. Dans la fenêtre `Hierarchy`, cliquer l'objet racine `P04 Navigation Sandbox Generated`.
4. Dans son `Inspector`, trouver le composant `NavMesh Surface`. Cliquer son bouton `Bake` — selon la version du package, il peut être libellé `Build NavMesh`.
5. Dans la fenêtre `Scene`, activer le bouton `Gizmos` situé en haut à droite. Les sphères jaunes représentent les attentes et la ligne magenta le seuil. Ces repères sont surtout destinés à la vue Scene, pas à la vue Game.
6. Cliquer le bouton Play de Unity, puis déplier `P06 Door Traversal Stress` dans la Hierarchy pour suivre les quatre capsules.

Sous cette racine, les objets `P06 Clearance A 1..4` et `P06 Clearance B 1..4` sont les dégagements latéraux ajoutés par la correction. Il suffit de les observer ou de les sélectionner ; ne pas les déplacer manuellement.

Résultat attendu : quatre capsules venues des deux côtés se succèdent une par une. Elles changent de côté et repartent jusqu'au message `P06 door stress completed 20 traversals.`.

Signe d'échec : deux capsules dans le seuil, aucun progrès pendant plusieurs secondes, `NpcDoorTraversal failed`, warning NavMesh répété ou compteur qui n'atteint jamais 20.

### 3. Vérifier l'interaction joueur

Ouvrir `SampleScene`, passer en Play Mode, viser une porte existante à moins de trois mètres et appuyer sur E. Elle doit encore s'ouvrir puis se refermer. Ne pas sauvegarder de déplacement de scène effectué uniquement pour ce test.

## Limites

- Aucun verrou, droit d'accès ou système de faction n'est ajouté.
- La porte reste ouverte tant que le joueur ne la referme pas ; une fermeture automatique n'est pas ajoutée.
- Les deux échecs historiques sont corrigés dans le code mais leur nouveau résultat Unity reste à confirmer avant le Bake et la porte H2.
